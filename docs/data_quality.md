
# 서울 지하철 원본 데이터 품질 진단 및 관리 기준

이 문서는 진단 시점별 기록과 후속 구현 결과를 함께 보존한다. 앞선 “아직 미변경” 표기는 해당 진단 단계의 상태다. 신규 품질 Mart의 실제 구현·검증 상태는 문서 후반의 “일별 품질 Mart 구현 및 검증” 절을 기준으로 확인한다.

## 진단 범위와 기준 시점

- 진단일: 2026-10-12. 미래 시각 SQL 검증 기준 시각: 17:40:44 KST.
- 대상: `public.subway_arrival` 31,987건과 기존 dbt Staging 및 Mart 3개.
- 원본 전체 행 체크섬: `defec9f4b54d89fcf40ad4752c847920`.
- 본 작업은 읽기 전용 진단과 문서 작성이다. 원본, 모델, 테스트, Metabase용 구조를 변경하지 않았다.
- 직전 전체 dbt 실행: 모델 4개 성공. 테스트 PASS=29, WARN=1, ERROR=0.
- WARN은 기존 `warn_source_exact_duplicates`의 중복 그룹 8개 감지 결과다. 이번 문서 작업에서 dbt를 다시 실행하지 않았다.

## 시간 컬럼의 의미

확인된 코드 경로:

1. `src/extract.py`는 API 응답을 raw JSON에 저장한다. `datetime.now()`로 만든 `collected_at`은 배치 수집 완료 시각이며 파일명에도 사용된다.
2. `src/transform.py`는 API의 `recptnDt`를 시간대 없는 datetime으로 파싱해 `received_at` 문자열로 저장한다.
3. `src/load.py`는 해당 값을 그대로 삽입한다. 원본 컬럼은 `timestamp without time zone`이다.

`received_at`은 API가 제공한 수신 시각이며 실제 파이프라인 수집 시각과 다르다. 프로젝트에서는 한국 시간으로 해석한다. API 문자열 자체에는 시간대 표시가 없다. Windows는 KST, Airflow 컨테이너 OS와 기본 시간대는 UTC, PostgreSQL 세션은 `Etc/UTC`다. DAG의 시작일 시간대는 `Asia/Seoul`이다.

Airflow가 만든 배치 파일명과 `collected_at`은 UTC 시계값이지만 오프셋이 생략돼 있다. 아래 배치 비교에서는 컨테이너 수집 시각에 9시간을 더해 KST로 표시했다. 과거 파일 전체의 실행 환경을 파일명만으로 확정할 수는 없다. `pipeline_load_history.loaded_at`은 시간대가 있는 적재 시각으로, 수집 시각이나 API 시각을 대체하지 않는다.

현재 Mart는 API 시각의 날짜·시간을 직접 추출한다. 해당 컬럼이 시간대 없는 timestamp이므로 DB의 UTC 설정에 따른 자동 9시간 이동은 없다. 분석 지표는 API 응답 레코드의 집계이며 실제 열차 운행 횟수, 고유 도착 사건 수 또는 수집 시각별 관측량과 동일하지 않다.

## 중복 판정과 관측 결과

`metro_dbt/tests/warn_source_exact_duplicates.sql`은 다음 10개 컬럼을 모두 묶어 `count(*) > 1`인 그룹을 반환한다.

```text
subway_id, station_id, station_name, direction, train_line,
train_no, arrival_seconds, arrival_message, current_station, received_at
```

`id`, 배치 식별자, 수집 시각은 판정에 포함되지 않는다. 따라서 다른 배치에서 동일 응답을 재관측해도 중복으로 경고한다. SQL GROUP BY의 NULL도 같은 그룹으로 모이지만 이번 원본에는 아래 11개 컬럼의 NULL이 없다. 테스트의 `WARN 8`은 중복 레코드 수가 아니라 결과 그룹 수다.

### 배치 파일과 적재 이력 증거

원본에서 발견한 10개 컬럼 조합을 보관된 모든 processed 파일과 정확히 비교했다. 각 그룹의 일치 파일 수는 DB 그룹 건수와 같고, 각 파일에는 일치 행이 한 번씩 존재한다. 해당 raw 파일에서도 같은 역·열차번호·API 시각이 한 번씩 존재한다.

| 대상 그룹 | 일치 배치 파일(UTC 파일명 시각) | 배치 수 | 수집 완료 시각(KST 해석) | 적재 이력 |
|---|---|---:|---|---|
| 1~4 | `subway_batch_20261001_082104_cleaned.json`, `subway_batch_20261001_082303_cleaned.json` | 각각 2 | 10-01 17:21:04, 17:23:03 | 없음 |
| 5 | `20261003_153005` ~ `20261003_203005`의 30분 간격 파일 | 11 | 10-04 00:30 ~ 05:30 | 없음 |
| 6 | `20261005_153005` ~ `20261005_203006`의 30분 간격 파일 | 11 | 10-06 00:30 ~ 05:30 | 없음 |
| 7 | `20261009_153005` ~ `20261009_183058`의 30분 간격 파일 | 7 | 10-10 00:30 ~ 03:30 | 각 배치 1개 |
| 8 | `20261011_153010` ~ `20261011_203012`의 30분 간격 파일 | 11 | 10-12 00:30 ~ 05:30 | 각 배치 1개 |

표의 축약 파일명은 `subway_batch_<날짜_시각>_cleaned.json` 형식이다. 중간 파일의 초 단위는 배치마다 다르다. 적재 이력 전체는 149개이며 가장 이른 `loaded_at`은 2026-10-07 15:00:12 UTC다. 따라서 앞선 배치의 이력 부재는 적재 실패나 중복 적재의 증거가 아니다.

**확인된 사실:** 동일한 정제 레코드가 서로 다른 보관 배치에서 반복 관측됐고, DB 건수도 그 관측 횟수와 일치한다. 조사된 파일 내부에서 해당 중복 조합이 두 번 들어간 사례는 없다. 이력이 있는 그룹 7~8의 배치마다 적재 이력 한 개가 존재한다. 현재 loader는 파일 basename을 batch_id로 사용하며 같은 batch_id의 재적재를 건너뛴다.

**해석:** 이번 8개 그룹은 동일 배치의 반복 적재보다 서로 다른 수집에서 동일 API 레코드를 반복 기록한 패턴으로 설명된다. 관측 이력 보존 목적에서는 허용할 수 있지만, 잠실의 반복 시각 자체는 시간 품질 문제다. API 전체 응답이 통째로 동일했다는 뜻은 아니다.

**확정할 수 없는 사항:** 원본 행에 batch_id가 없으므로 개별 ID와 배치의 직접 연결은 불가능하다. 이력이 없는 과거 배치의 실제 적재 횟수 및 실행 경위를 완전히 증명할 수 없다. API가 같은 값을 계속 반환한 이유도 확인되지 않았다. 위 증거만으로 전체 적재 시스템에 중복 적재가 전혀 없다고 단정하지 않는다.

## 미래 시각 이상값 12건

2026-10-12 17:40:44 KST에 원본 시각을 한국 현재 시각과 비교해 미래값 12건을 확인했다. 모두 잠실·하행·모란행 - 석촌방면, `received_at=2026-10-12 23:59:56`, `arrival_seconds=0`이다.

- 열차 8241: 동일 레코드 11건, 중복 그룹 8에 해당한다.
- 열차 8003: 1건. 열차번호가 달라 위 10개 컬럼 기준 중복 그룹에는 포함되지 않는다.
- raw 파일 `subway_batch_20261011_153010.json`부터 `subway_batch_20261011_203012.json`까지 11개에서 같은 미래 API 시각을 확인한 기존 조사와 일치한다. 앞 10개 파일은 각 1건, 마지막 파일은 열차 8241과 8003 각 1건이다.
- 한국 수집 시각은 10-12 00:30~05:30경인데 API 값은 같은 날 23:59:56이다. raw에 이미 존재하므로 ETL의 시간대 변환 오류로 생성된 값은 아니다.

**확인된 영향:** Hourly Mart의 `2026-10-12 / 23시 / 잠실 / 하행` 그룹은 12건이다. Daily Mart의 같은 날짜·역·방향·노선 그룹은 30건, 평균 0.00초이고 `latest_received_at`은 이상값으로 잡힌다. Arrival Mart의 해당 그룹 최근 시각도 영향을 받는다. 날짜·시간별 관측량, 최근성 지표와 평균값 해석에 주의가 필요하다. 12건은 당일 다른 시간대에 수집된 기록이므로 실제 수집 시각별 집계와 다르다.

전체 평균은 239.19초다. 영향 확인용 읽기 전용 계산으로 12건을 제외하면 239.28초다. 이는 민감도 비교일 뿐, 실제 원본 또는 Mart에서 제외하지 않았다. 미래값 판정은 시간이 지나면 사라지므로 현재 시각 검사만으로 과거 수집 당시의 이상을 보존할 수 없다.

**추정:** 비정상·고정된 API 시각 또는 공급 시스템의 시각 문제일 수 있다. 자정 근처 반복 패턴이 있으나 원인을 단정할 증거는 없다. 이전 진단의 최신 배치도 수집 완료 약 16:30:07 KST 대비 API 최대 16:34:28로 약 4분 21초 앞서 있어, 허용 오차는 별도 검토가 필요하다.

## 품질 관리 기준 제안

아래는 향후 구현 제안이며 이번 작업에서 모델·테스트·원본에 적용하지 않았다.

| 항목 | 검증 기준 | 처리 방안 |
|---|---|---|
| 중복 | 현재 10개 컬럼 완전 중복을 WARN으로 집계. 배치 간 반복 관측과 동일 batch_id 재적재를 구분. 배치별 행 수·내용 체크섬·적재 이력 확인 | 관측 원본은 보존. batch_id와 관측 ID를 연결하고 동일 배치 재적재는 방지. 고유 사건 분석은 별도 파생 모델에서 식별 규칙 승인 후 수행 |
| 시간 이상값 | 한국 현재 시각보다 미래인 값, 배치 수집 시각보다 앞선 값, 오래된 API 시각을 각각 측정. `received_at`의 한국 시간 해석 명시 | 원본을 보정하지 않고 품질 플래그·사유·진단 시각 보존. 먼저 경고 운영. 수집 대비 미래 허용 오차와 오래된 값 기준은 공급 데이터·운영 주기에 근거해 별도 합의 |
| NULL | id, 역, 방향, 노선, 수신 시각, 도착시간 등 집계·추적 필수 컬럼 NULL=0 및 id 유일성. 현재 검사는 11개 원본 컬럼 모두 NULL=0 | 필수값 누락은 오류로 알리고 별도 검토. 선택적 메시지 컬럼은 의미에 맞게 경고 여부 결정. 임의 기본값이나 0으로 채우지 않음 |
| 도착 예정 시간 범위 | 정수·NULL 아님·음수 아님 확인. 이번 관측은 0~3,600초, 음수 0건·3,600초 초과 0건·0초 10,527건 | 음수는 오류 후보. 3,600초 초과는 현재 관측 범위 기반 경고 후보이며 API 보장 상한이 아님. 0초는 제거하지 않고 도착 메시지와 함께 해석. 유효 상한·0의 의미는 추후 확인 |
| 원본/Mart 정합성 | 각 Mart 건수 합계=동일 스냅샷 원본 건수, 집계키 중복=0, 원본 직접 재집계와 양방향 차이=0, 최소≤평균≤최대 | 차이가 있으면 원본을 수정하지 않고 모델·실행 시점·필터·시각 해석을 조사. 운영 중에는 같은 스냅샷/배치 경계로 비교 |

원본 보존 Mart와 품질 필터를 적용한 분석 모델을 구분해야 한다. 필터 적용 시 제외 사유·건수·전후 합계를 함께 제공하고 기존 Metabase 컬럼과 기존 집계 의미를 유지하는 별도 변경 계획을 마련한다. 단순 중복 삭제는 반복 관측의 의미를 잃게 할 수 있다.

## 재현용 읽기 전용 SQL

```sql
BEGIN TRANSACTION READ ONLY;

-- 원본 건수 및 ID 순서에 따른 전체 행 체크섬
SELECT count(*),
       md5(string_agg(md5(row_to_json(t)::text), '' ORDER BY id)) AS checksum
FROM public.subway_arrival AS t;

-- 중복 그룹 수, 관련 레코드 수, 초과 수
WITH duplicates AS (
    SELECT count(*) AS n
    FROM public.subway_arrival
    GROUP BY subway_id, station_id, station_name, direction, train_line,
             train_no, arrival_seconds, arrival_message, current_station, received_at
    HAVING count(*) > 1
)
SELECT count(*) AS duplicate_groups, sum(n) AS related_rows,
       sum(n - 1) AS excess_rows
FROM duplicates;

-- 실행 시점 기준 미래 API 시각: 시간 경과에 따라 결과가 달라진다.
SELECT now() AT TIME ZONE 'Asia/Seoul' AS checked_at_kst,
       count(*) FILTER (
           WHERE received_at > now() AT TIME ZONE 'Asia/Seoul'
       ) AS future_rows
FROM public.subway_arrival;

-- 이미 확인한 이상 시각을 고정 조건으로 추적
SELECT id, station_name, direction, train_no, received_at
FROM public.subway_arrival
WHERE received_at = TIMESTAMP '2026-10-12 23:59:56'
ORDER BY id;

-- 범위 진단
SELECT min(arrival_seconds), max(arrival_seconds),
       count(*) FILTER (WHERE arrival_seconds IS NULL) AS null_rows,
       count(*) FILTER (WHERE arrival_seconds < 0) AS negative_rows,
       count(*) FILTER (WHERE arrival_seconds > 3600) AS above_observed_range,
       count(*) FILTER (WHERE arrival_seconds = 0) AS zero_rows
FROM public.subway_arrival;

COMMIT;
```

**추정 및 불확실성**

- 일부 노선에서 초 단위 ETA를 제공하지 않거나 0을 미산출 값으로 사용할 가능성이 있다. 노선별 100% 패턴과 위치 메시지가 이 가설을 뒷받침하지만 공식 명세가 이를 확정하지 않으므로 `ETA 미제공 확정`으로 표시하지 않는다.
- 요청 역 도착·출발 메시지의 0은 상태 표현과 양립할 수 있으나, 정확히 남은 시간 0초 또는 현재 탑승 가능을 입증하지 않는다. 오래된 응답, 코드·메시지 불일치 및 제공 지연도 고려해야 한다.
- API 원천 규칙, 노선별 ETA 제공 여부, 0의 의미는 제공기관 확인이 필요하다. 실제 도착 시간이나 충분히 촘촘한 동일 열차 추적 자료가 없어 ETA 정확도·오차·실제 대기시간을 계산할 수 없다. 이번 진단은 값의 의미와 일관성 검증이다.

양수값 비율은 **수치 표본의 제공 범위** 지표이지 검증 완료된 ETA 정확도 또는 신뢰도 점수가 아니다. 시간 이상값 등을 제외한 지표가 필요해지면 별도 이름·명시적 필터·사유별 건수·중첩 사유 집계를 정의한다. 이번 양수 평균에는 양수 시간 이상값을 별도로 제외하는 필터를 넣지 않았다.

### dbt 후속 변경 계획 — SQL·모델·테스트는 아직 미변경

1. **수집 계층과 원본 스키마 계획:** 향후 신규 관측에 `arvlCd`, `arvlMsg2`, `arvlMsg3`, `ordkey`, `btrainSttus`, `batch_id`, 오프셋 있는 `collected_at`을 보존한다. 이는 이번 승인 범위 밖의 별도 변경이다. 과거 `arvlCd` 복원은 raw와 원본 ID의 연결 정책을 먼저 정하고 이번 다중집합 대조만으로 자동 UPDATE하지 않는다. 원본 행을 바꾸지 않는 별도 관측 증거 테이블 또는 파생 모델도 검토할 수 있다.
2. **Staging/중간 모델:** `arrival_seconds` 원문 수치를 유지하고 `arrival_seconds_is_zero`, `arrival_message_category`, `arrival_status_code`(확인된 출처 포함), `status_message_conflict`, `eta_semantics_uncertain`을 추가하는 별도 변경안으로 작성한다. raw 코드가 없는 행의 상태를 메시지에서 추정하면 `inferred` 출처를 표시하고 코드와 동일 취급하지 않는다.
3. **세 Mart:** 기존 `avg_arrival_seconds`의 전체 평균 의미를 보존하며 `zero_arrival_count`, `positive_arrival_count`, `null_arrival_count`, `negative_arrival_count`, `zero_arrival_rate`, `positive_arrival_rate`, `arrival_seconds_sum`, `positive_arrival_seconds_sum`, `avg_positive_arrival_seconds`를 추가한다. rate는 0~1로 저장하고 화면에서 %로 표시하도록 계약한다. 통계 재집계는 반올림 전 합/건수를 사용한다.
4. **집계 단위:** 기존 Arrival은 역명·방향·행선지, Daily는 여기에 날짜, Hourly는 날짜·시간·역명·방향이다. 현재 `train_line`은 `trainLineNm`(행선지방면)이며 호선 ID가 아니다. 호선별 비교를 지원하려면 `subway_id`, `station_id`가 포함된 신규 Mart를 만들거나 기존 모델의 grain 변경과 Metabase 의존성을 함께 검토한다. 기존 Hourly에는 호선이 없으므로 현재 결과만으로 호선별 양수 표본 차이를 분해할 수 없다.
5. **기간 필터:** 기존 Arrival에는 날짜가 없어 `2026-09-30` 이후 필터를 정확히 걸 수 없다. 원본/Staging 기반 분석 쿼리나 날짜를 가진 Mart를 사용하고, 현재 전체 31,987건을 이번 분석 31,982건과 섞지 않는다. 진단용 날짜를 모든 모델에 하드코딩하지 않는다.
6. **테스트:** raw↔DB 배치 정합성, 범주 건수 합, 비율 범위, 양수 평균·합·건수 일치, 양수 건수 0일 때 NULL, 상태 도메인, 메시지 정합성 WARN, 같은 grain 양방향 재집계를 추가하는 계획이다. 양수값이 없는 그룹도 Mart 행과 건수는 유지한다. 기존 평균의 최소≤평균≤최대 검증은 유지하고 양수 평균은 양수값 최소·최대와 비교한다.

다음은 후속 구현 시 참고할 **읽기 전용 지표 정의 SQL**이다. 이번 작업은 SELECT 진단만 수행했고 dbt 모델을 변경하지 않았다.

```sql
BEGIN TRANSACTION READ ONLY;

SELECT station_name, subway_id, station_id, direction,
       count(*) AS observation_count,
       count(*) FILTER (WHERE arrival_seconds = 0) AS zero_arrival_count,
       count(*) FILTER (WHERE arrival_seconds > 0) AS positive_arrival_count,
       count(*) FILTER (WHERE arrival_seconds IS NULL) AS null_arrival_count,
       count(*) FILTER (WHERE arrival_seconds < 0) AS negative_arrival_count,
       count(*) FILTER (WHERE arrival_seconds = 0)::numeric
           / NULLIF(count(*), 0) AS zero_arrival_rate,
       count(*) FILTER (WHERE arrival_seconds > 0)::numeric
           / NULLIF(count(*), 0) AS positive_arrival_rate,
       sum(arrival_seconds) AS arrival_seconds_sum,
       coalesce(sum(arrival_seconds) FILTER (WHERE arrival_seconds > 0), 0)
           AS positive_arrival_seconds_sum,
       avg(arrival_seconds) AS avg_all_arrival_seconds,
       avg(arrival_seconds) FILTER (WHERE arrival_seconds > 0)
           AS avg_positive_arrival_seconds
FROM public.subway_arrival
WHERE received_at >= TIMESTAMP '2026-09-30 00:00:00'
GROUP BY station_name, subway_id, station_id, direction;

ROLLBACK;
```

### Metabase 후속 변경 계획 — 차트는 아직 미변경

- 현재 dbt의 세 평균은 `avg(arrival_seconds)`로 0을 포함한다. 사용자가 알려준 “역별 평균 차트가 0초 포함”이라는 동작과 일치한다. 로컬 Metabase `/api/health`는 정상이나 `/api/card`, `/api/dashboard`는 인증 없이 401을 반환했다. **실제 저장된 카드 SQL, 카드 ID, 추가 필터 및 평균 재집계 방식은 이번 작업에서 직접 확인하지 못했다.** 그러므로 사용자 설명과 모델 SQL의 확인 범위를 구분한다. 로그인 정보나 세션을 임의로 변경하지 않았다.
- 기존 차트를 후속 작업에서 `API 도착 예정 시간 평균 — 전체 값(0초 포함)`으로 명확히 이름 붙이고 `API 도착 예정 시간 평균 — 양수값만(0초 제외)`을 병렬 제공한다. 설명에 “API 응답 관측의 조건부 평균이며 실제 승객 대기시간 아님”을 명시한다.
- 0초 비율, 전체 관측 수, 양수 관측 수·비율을 같은 기간·역·호선·방향 필터로 연동한다. 상태×메시지 품질 표와 노선별 제공 범위 표를 추가한다. 양수 건수 0인 그룹은 **양수 시간 표본 없음**으로 표시하고 시간값을 0으로 채우지 않는다.
- 여러 Mart 행을 역 단위로 합칠 때 `AVG(avg_arrival_seconds)` 또는 `AVG(avg_positive_arrival_seconds)`를 사용하지 않는다. 전체 평균은 `SUM(arrival_seconds_sum) / SUM(관측 중 NULL 아닌 건수)`, 양수 평균은 `SUM(positive_arrival_seconds_sum) / NULLIF(SUM(positive_arrival_count), 0)`로 재계산한다. 현재처럼 NULL이 없을 때에만 전체 건수를 전체 평균의 분모로 사용할 수 있다. 비율도 그룹 비율의 단순 평균 대신 합계 건수로 계산한다.
- 실제 차트 정의를 인증된 읽기 전용 접근으로 확인한 후 사용 테이블·날짜 필터·집계 grain·단위·NULL 표시·재집계 방식을 검증하고 변경안을 만든다. 0초 제외를 모든 차트의 전역 필터로 적용하면 관측량·품질 지표에서도 0이 사라지므로, 양수 평균 계산 내부에만 조건을 적용한다.
- 출시 전 검증 예: 전체 평균 239.2166초, 양수 평균 356.5395초, 0초 10,524건/31,982건을 동일 기간에서 재현; 강남 호선별 분리; 100% 0 노선은 양수 평균 NULL과 표본 없음 표시; 날짜·방향 필터에 건수와 비율이 함께 변경되는지 확인한다.

## 일별 품질 Mart 구현 및 검증 — 2026-10-12

### 구현 범위와 지표 계약

신규 `analytics.mart_arrival_quality_daily`를 table 모델로 추가했다. 소스는 기존 `stg_subway_arrival`이며 기존 모델 SQL·YAML·테스트·컬럼 이름은 변경하지 않았다. 신규 메타데이터는 별도 `metro_dbt/models/marts/arrival_quality_schema.yml`에 정의했다. 기존 Git 변경사항을 보존했다.

집계키는 **`received_date, station_name, subway_id, direction`**이다. `received_date = received_at::date`이며 기존 시간대 없는 API 시각을 KST로 해석한다. 프로젝트의 “API 수신 날짜” 명칭과 달리 공식적으로는 도착정보 생성일이며, 파이프라인 수집일이 아니다. 실제 호선 ID인 `subway_id`를 사용하고 행선지 문자열 `train_line`은 집계키에 사용하지 않는다. 역은 이번 요청에 따라 역명으로 구분한다.

모든 날짜·원본 관측·반복 관측·미래 시각 이상값을 포함한다. 9월 30일 기준을 모델 필터로 하드코딩하지 않았다. Metabase에서 `received_date >= DATE '2026-09-30'`으로 범위를 선택할 수 있다.

| 컬럼 | 정의 및 NULL 계약 |
|---|---|
| `arrival_record_count` | 전체 API 도착정보 관측 레코드 수. 실제 열차 운행·도착 사건 수가 아님 |
| `zero_arrival_count` | `arrival_seconds = 0`인 건수 |
| `positive_arrival_count` | `arrival_seconds > 0`인 건수 |
| `zero_arrival_rate` | 0초 건수 / 전체 건수, numeric 0~1. 화면에서 %로 표시 |
| `avg_arrival_seconds` | 0초 포함 전체 수치 평균. SQL AVG에 따라 NULL은 제외하며 전부 NULL이면 NULL |
| `avg_positive_arrival_seconds` | 양수값만의 조건부 평균. 양수 건수 0이면 NULL. 실제 평균 대기시간을 의미하지 않음 |
| `positive_arrival_seconds_sum` | 양수값 합계. 양수 건수 0이면 0 |
| `null_arrival_count` | NULL 건수. 범주별 건수 정합성 및 전체 평균 재집계 분모에 사용 |
| `negative_arrival_count` | 음수 건수. 정상·오류 여부와 별개로 원본 관측을 보존·측정 |
| `arrival_seconds_sum` | 0초·음수를 포함하는 전체 수치 합계. NULL 제외, 전부 NULL이면 NULL |

마지막 세 보조 지표는 범주별 정합성과 안전한 평균 재집계를 지원한다. 모델의 평균은 반올림하지 않고 저장하며 화면 표시 단계에서만 반올림한다. 양수 평균에 `not_null`을 적용하거나 NULL을 0으로 채우지 않는다. 기존 진단에서 제안한 상태 코드·배치 추적·품질 플래그는 이번 Mart 작업에 포함하지 않았다.

### Metabase에서 사용할 수 있는 지표

신규 테이블 `analytics.mart_arrival_quality_daily`를 사용해 날짜·역·호선·방향별 관측 건수, 0초 비율, 전체 수치 평균, 양수 조건부 평균을 표시할 수 있다. 여러 날짜·방향을 합칠 때 평균·비율의 단순 평균을 사용하지 않는다.

```sql
SELECT station_name, subway_id,
       SUM(arrival_record_count) AS observation_count,
       SUM(zero_arrival_count) AS zero_count,
       SUM(positive_arrival_count) AS positive_count,
       SUM(zero_arrival_count)::numeric
           / NULLIF(SUM(arrival_record_count), 0) AS zero_rate,
       SUM(arrival_seconds_sum)::numeric
           / NULLIF(SUM(arrival_record_count - null_arrival_count), 0)
           AS avg_all_seconds,
       SUM(positive_arrival_seconds_sum)::numeric
           / NULLIF(SUM(positive_arrival_count), 0) AS avg_positive_seconds
FROM analytics.mart_arrival_quality_daily
WHERE received_date >= DATE '2026-09-30'
GROUP BY station_name, subway_id;
```

시간 단위는 초이고 비율은 0~1이다. 양수 평균 NULL은 “양수 시간 표본 없음”으로 표시한다. 양수 건수·전체 건수를 함께 표시하고, 양수 평균을 실제 평균 대기시간이나 ETA 정확도라고 설명하지 않는다. 기존 테이블을 사용하는 차트를 자동 전환하지 않았으며 신규 차트 연결은 별도 작업이다.

## 동일 배치 재실행 및 중복 적재 방지 검증 — 2026-10-13

### 검증 목적

동일한 정제 JSON 파일을 다시 적재할 때 `public.subway_arrival`에 중복 행이 추가되는지 확인했다. 원본 데이터를 삭제하거나 수정하지 않고 이미 처리한 배치에 대해 재실행 테스트를 수행했다.

### 검증 환경과 사전 확인

| 항목 | 검증 당시 상태 |
|---|---|
| PostgreSQL 원본 데이터 | 31,987건 |
| `public.pipeline_load_history` | 존재 |
| 배치 이력 테이블 기본키 | `PRIMARY KEY (batch_id)` |
| 기록된 적재 배치 | 149개 |
| 재실행 대상 파일 | `subway_batch_20261012_073007_cleaned.json` |
| 대상 배치의 이력상 행 수 | 88건 |
| 컨테이너의 대상 정제 파일 | 존재 확인 |

`src/load.py`는 정제 파일의 basename을 `batch_id`로 사용한다. 배치 이력은 `ON CONFLICT (batch_id) DO NOTHING RETURNING batch_id`로 선점하며, 이미 처리된 배치로 판정되면 원본 테이블에 행을 추가하지 않고 종료한다. 이력 기록과 도착정보 삽입은 하나의 트랜잭션으로 처리한다.

### 실행 및 검증 결과

기록된 배치 파일을 다시 지정해 `load_data()`를 호출했다.

```cmd
docker exec -w /opt/airflow seoul-metro-airflow python -c "from src.load import load_data; n = load_data('data/processed/subway_batch_20261012_073007_cleaned.json'); print('inserted_count:', n); assert n == 0, '중복 적재 방지 테스트 실패'"
```

출력:

```text
이미 처리된 배치이므로 skip: subway_batch_20261012_073007_cleaned.json
inserted_count: 0
```

재실행 직후 PostgreSQL에 대해 원본 건수와 적재 이력 건수를 재조회했다.

```sql
SELECT
    (SELECT COUNT(*) FROM public.subway_arrival) AS total_rows,
    (SELECT COUNT(*) FROM public.pipeline_load_history) AS recorded_batches;
```

검증 결과 `total_rows = 31987`, `recorded_batches = 149`로 재실행 전과 동일했다. **이미 등록된 단일 배치를 다시 실행했을 때 추가 적재가 발생하지 않는 동작을 확인했다.**

### 원본의 동일 레코드 반복 관측과 구분

기존 완전 중복 8개 그룹, 관련 48건, 초과 40건은 위의 배치 단위 멱등성 검증과 구분한다. 8개 그룹 모두 서로 다른 Raw JSON 파일에 동일한 비교 대상 API 필드 조합이 반복 존재했다. 각 Raw 파일에서 해당 조합은 한 번씩 확인됐다. 특히 잠실 8호선 열차 8241, API 생성 시각 `2026-10-12 23:59:56`인 레코드는 서로 다른 Raw 파일 11개에서 각각 1건 확인됐다. 비교한 것은 앞서 정의한 10개 필드의 대응값이며 API 응답의 모든 필드가 동일하다는 뜻은 아니다.

따라서 관측된 초과 중복은 동일한 배치의 재적재 오류보다는 **서로 다른 수집 배치에서 동일한 API 레코드가 다시 관측된 패턴**으로 설명된다. 다만 원본 테이블의 개별 ID에 `batch_id`가 연결되지 않아 모든 과거 적재 경위를 입증할 수는 없고, API가 동일 값을 반복 반환한 이유도 확정하지 않았다.

### 한계와 후속 관리

- 이번 테스트는 **이미 이력이 존재하는 한 개 배치**에 대한 재실행 검증이다. 모든 배치, 동시 실행 상황, 과거 이력 미등록 파일의 멱등성까지 실증한 것은 아니다.
- 배치 단위 중복 차단은 동일한 파일명을 기준으로 작동한다. 서로 다른 배치 파일에 동일한 관측 레코드가 포함되는 현상까지 제거하지 않는다.
- `load.py`의 `allow_legacy=True` 경로는 이력 테이블이 없는 환경에서 배치 중복 방지를 적용하지 않으므로, 향후 이력 테이블을 필수 조건으로 설정할지 별도 검토한다.
- 기존 31,987건 및 반복 관측 데이터는 보존했다. 중복 그룹을 임의로 삭제하거나 데이터별 UNIQUE 제약조건을 추가하지 않았다.
